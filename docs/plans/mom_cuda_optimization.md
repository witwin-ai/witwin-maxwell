## (a) GMRES true-residual cost

- **Current behavior:** scalar `_single_gmres` evaluates `b-action(x)` initially and after every candidate (`witwin/maxwell/mom/linalg.py:907`, `:965`), in addition to the Arnoldi action (`:939`). It therefore uses **2k+1 operator applications** for k ordinary successful steps, before extra surrounding admission work. Flexible GMRES also checks every candidate (`:1099`). This is roughly twice the operator cost, not a measured 2× whole-solve slowdown. History drives convergence, stagnation and finite-closure restart (`:970`, `:975`, `:978`). Block GMRES is a separate algorithm.
- **Proposal/gain:** explicitly configured residual checkpoints could use the small Arnoldi least-squares residual to request checks, with actual unscaled residual mandatory before success, restart, closure and terminal exit. Preserve the existing per-step policy as the reference contract. Estimate: at check interval q, operator work approaches k+k/q instead of 2k; upper-bound speedup ~2/(1+1/q), below 2×, with no guarantee when orthogonalization/preconditioning dominates. Preserving exact stagnation semantics may require checks that reduce this gain; decide that policy before implementation.
- **Acceptance:** direct-LU outputs, unchanged-policy currents/history/configuration, original operator actions and block-GMRES behavior must stay bit-identical. The new policy may change iterates, iteration counts and histories within tolerance, but must satisfy the same unscaled rtol/atol and compressed/original-operator gates; no false success or relaxed maxiter/stagnation/closure behavior. A changed stagnation sampling contract needs explicit review, not implicit equivalence.
- **Existing controls:** `tests/mom/test_linalg.py`, `test_gmres_finite_closure.py`, `test_right_preconditioner_hook.py`, and v4 accepted public backend solves. Include right-preconditioned FGMRES, finite closure, zero RHS, exhausted budgets and stagnation through these existing cases. At most one targeted new checkpoint-policy regression if existing cases cannot express it.
- **Pins/epoch:** new policy requires new configuration identity and new iterative numerical/history pins where present; unchanged-policy/direct pins must remain exact. V3 receipts remain immutable, including their source hashes; even bit-identical dense results do not authorize a changed runtime under the v3 identity. Land **last in v5**, after an old/new residual and cost report and explicit stopping-policy review.

## (b) FMM/H2 node and block batching

- **Current behavior:** `FMMConfig.far_action_batch=1` (`witwin/maxwell/mom/fmm_config.py:18`); regional FAR then loops through individual couplings (`fmm_regional.py:270`). Explicit batches 2–32 already stack moments and apply compact kernels while retaining original per-pair accumulation (`:276`, `:285`). Batch=1 omits the field from the historical payload (`fmm_config.py:107`); changing the default changes configuration identity. Do not describe the existing explicit batch path as new work.
- H2 computes each coupling separately (`witwin/maxwell/mom/h2.py:198`), with Python node loops in upward/downward transfers (`h2_basis.py:178`, `:199`). H2 has no `far_action_batch` setting; FMM's setting must not be attributed to it.
- **Proposal/gain:** qualify/use existing compact FMM batching first; then group H2 equal-rank/shape blocks and tree levels for batched CUDA contractions, preserving logical interaction and accumulation order. Native kernels are justified only for remaining launch/packing overhead. Estimate **1.5–3× action throughput** on small-block, launch-bound workloads; no measured gain or setup speedup is claimed. Extra transient stacks must fit the lane budget.
- Historical evidence: default actions and fourteen archived payloads remained exact in the previous opt-in batch change; full original weak error 3.98e-16 and Hermitian-dot error 2.23e-16 were observed (`docs/assessments/sie_bounded_compact_far_execution.md:5`, `:9`). The 121,388,800-byte worst visible workspace is an estimate, not total peak (`:7`). H2 still inherits costly H setup (`docs/plans/mom_large_scale_learned_operators.md:58`, `:375`).
- **Acceptance:** geometry, quadrature, retained coefficients/near blocks, pair identities, default batch=1 payloads and saved-current restore bytes stay bit-identical. Batch contractions may differ by roundoff: keep existing weak-action, Hermitian-dot and first/higher current-gradient tolerances, all original solve/admission gates, and v4 Bench/Mie field screens. Ordered accumulation is required; do not assume a batched GEMM itself is bit-identical.
- **Existing controls:** `tests/mom/test_bounded_compact_far.py`, `test_fmm_compact_batch.py`, `test_fmm_compact_layout_batch.py`, `test_fmm_batch_admission.py`, `test_h2.py`, `test_h2_basis.py`, `test_h2_operator.py`, `test_hmatrix_public.py`; retain the exact parameters reviewed for v4. The bounded-FAR physical fixture and its 15 noncontiguous RHS/gradient checks are at `test_bounded_compact_far.py:25`, `:49`.
- **Pins/epoch:** no old payload/restore re-pinning for unchanged defaults. A selected batch/default or reordered arithmetic needs a new producer identity and new affected numerical pins with an old/new delta report; never rewrite original archived payloads. V3 is not amended; v5 supersedes its runtime identity for changed files. Land **first in v5**, separate FMM and H2 results within that epoch.

## (c) Complex64 pFFT batching

- **Current behavior:** grid storage is complex64 when configured, with float32 projection weights (`witwin/maxwell/mom/pfft_operator.py:66`); `_scatter` uses `index_add_` (`:98`), `_potential` loops over channels (`:130`). D/K already share four forward spectra, but forward and inverse transforms remain separate channel calls (`:150`). Whole-system `_action` flattens and serializes RHS (`pfft_system.py:204`). Exact precorrection grid entries are accumulated in complex128 (`pfft_operator.py:206`); batching must retain that precision.
- **Proposal/gain:** batch channels and bounded RHS with explicit spatial FFT dimensions; fuse projection/gather only after preserving their reductions and PyTorch current-gradient contract. Keep exact near corrections and lifting unchanged. Estimate **1.2–2× action throughput**, mainly fewer launches and reused transforms; larger work grids can erase the gain. No 2× total preparation claim: historical pFFT setup is dominated by exact integration/lifting (`docs/plans/mom_large_scale_learned_operators.md:1191`).
- **Acceptance:** mesh/grid choice, kernel samples, near-pair indices, complex128 exact correction entries, configuration and unchanged unbatched outputs stay bit-identical. Batched FFT/scatter roundoff uses existing action/adjoint/dense and order/grid-refinement tolerances; add at most one targeted current-gradient comparison if coverage is missing. Reapply v4's 4λ Mie ≤0.5%, optical defect ≤1e-3, ≤200-iteration sparse-LU and original-residual gates.
- **Existing controls/drivers:** closed-surface `tests/mom/test_pfft_operator.py`, `test_pfft_public.py`, `test_pfft_lifting.py`, `test_pfft_clusters.py`; `benchmark/mom_pfft_acceptance.py`, `mom_pfft_accuracy.py`, `mom_pfft_sparse.py`. Open-sheet `test_pfft_efie.py` remains outside v4 claims; shared-kernel impact must be reviewed before landing, with that existing test admitted if its behavior is affected. Sparse-LU validation still requires all three locks and native memory accounting.
- **Pins/epoch:** source/core identities change even if sampled numbers match. New batched numerical results may require affected bitwise-baseline re-pinning; keep exact routing/correction and unbatched pins. V3 source-only pFFT coverage grants no numerical equivalence and its receipt is never rewritten. Land **second in v5**, preserving separate v4 evidence and a batch-size/memory record.
